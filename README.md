# banwords

Сервис опубликованных словарей SayPatch для danysik.ru. Node.js 22.18+, без
внешних runtime-зависимостей. Собственный контейнер `ghcr.io/modaniru/banwords`,
внутри Compose слушает `8080`; наружу — только через Caddy.

## API и Swagger

Источник контракта — [`openapi.json`](openapi.json). Справка без CDN:
`GET /api/banwords/docs`; спецификация: `GET /api/banwords/openapi.json`.
**При каждом изменении хендлеров обновлять OpenAPI в той же задаче.**
Все `/api/banwords/*` закрыты; `/healthz` — внутренний `204` для Docker.

| Метод | Путь | Ответ |
| --- | --- | --- |
| GET | `/api/banwords/catalog` | Текущий `saypatch-rules` v1 без обёртки: `format`, `version`, `variants`, `rules` |
| GET | `/api/banwords/dictionaries/{id}` | `{protocol:"sp/1",id,dictionaries:[{id,digest,words}]}` |
| GET | `/api/banwords/openapi.json` | OpenAPI 3.1 |
| GET | `/api/banwords/docs` | HTML-справка со ссылкой на OpenAPI |
| GET | `/healthz` | `204`, seed-файлы проверены до запуска HTTP |

`id` — 4 символа Base64url первых 24 бит SHA256. `digest` — полный SHA256
канонического JSON в hex. Канонизация совпадает с `extension/core.js`:
NFC → JavaScript lowercase → NFC, удаление дублей, **UTF-16 Array.sort()**,
`JSON.stringify(["sp",1,"dictionary",words])`, UTF-8. В запросах нет текста сообщений.

Неизвестный словарь — `404`; неправильный `id` — `400`; неподдерживаемый метод —
`405` + `Allow: GET`; лимит — `429` + `Retry-After`; недоступные JWKS — `503`
+ `Retry-After: 5`; непредвиденная ошибка — `500` без подробностей.

Коллизия короткого id — **HTTP 200 со всеми различными словарями**, без выбора
одного. Клиент проверяет формат, канонизацию и id каждого кандидата; полный digest
публикуется как дополнительный идентификатор состава для диагностики.
Если кандидатов несколько, сохраняется неоднозначность; неподтверждённое слово
не показывается. API ограничен 64 опубликованными версиями, до 50 слов в каждой
(до 100 UTF-16 единиц на слово); seed-файл — до 64 КиБ. Ответ может содержать до
8 совпадений; девятый различный словарь с тем же id останавливает публикацию
при старте сервиса. Клиент сохраняет все полученные кандидаты и неоднозначность.

Лимит запросов — 60/мин на `sub` владельца (включая справку), фиксированное окно.
В памяти не более 10000 активных владельцев; при заполнении новые получают `429`,
до освобождения истёкших окон. JWT — до 8 КиБ, заголовки HTTP — до 16 КиБ.

## Авторизация, выпуск и отзыв токенов

1. Суперадмин выдаёт пользователю права `banwords`, `banwords:tokens` и
   `banwords:dictionaries:read` (админка добавляет промежуточный узел
   `banwords:dictionaries`). Новым пользователям доступ автоматически не выдаётся.
2. Пользователь входит на сайте через Twitch и создаёт service-токен для
   `banwords`. Секрет `bw_…` показывается один раз; auth хранит его SHA256.
3. Расширение хранит секрет в изолированном контексте и делает запросы с
   `Authorization: Bearer bw_…`. Секрет не передаётся в MAIN-world страницы Twitch.
4. Caddy вырезает входящий `X-Auth-Token`, вызывает auth `/verify` и ставит
   внутренний JWT. Auth проверяет наличие/срок/отзыв service-токена, его service
   scope и **текущие** права владельца.
5. Banwords принимает только внутренний JWT с Ed25519 подписью из JWKS,
   `iss=danysik-auth`, `aud=banwords`, действующим `exp` и точным правом
   `banwords:dictionaries:read` (либо `superadmin`). Пользовательский `bw_…`
   напрямую сервис не принимает.

Управление выполняется с cookie-сессией через `GET/POST /api/auth/service-tokens`
и `DELETE /api/auth/service-tokens/{id}`. Создание принимает `{name,expiresInDays?}`,
срок — 1–90 дней (по умолчанию 90), максимум 20 активных токенов на владельца.
Секрет показывается только в ответе создания `{token,secret}`; список возвращает
только метаданные в `{tokens:[...]}`. Отзыв конкретного service-токена выполняется
на той же странице сайта через auth.
Снятие у владельца `banwords`, `banwords:tokens` или права чтения прекращает
авторизацию всех его токенов для этого сервиса. Уже скачанные локальные словари
отзыв не удаляет. Уже выданный внутренний
JWT действителен до своего `exp` (по умолчанию auth — 2 минуты); снаружи каждый
новый запрос проходит повторную проверку auth.

JWKS кешируются 300 с; неизвестный `kid` инициирует обновление не чаще раза в
5 с, одновременные запросы объединяются. Таймаут — 3 с, ответ — до 64 КиБ,
не более 16 ключей, редиректы запрещены. Истёкший кеш при недоступности auth
не используется. Для ротации auth некоторое время публикует оба ключа.
Слова, текст сообщений, заголовки и секреты не логируются.

## Публикация и версии

`data/versions/v1.json` — точная копия текущего
`extensions/twitch-bw-checker/examples/rules.default.json` на момент переноса:
**22 правила: 21 banword и safe «Денчик»**. Все пулы, категории, порядок и
`matchMode` сохранены. Полный словарь имеет id **`0dMf`**. Исключать safe-правило
нельзя: изменится id и перестанут читаться старые сообщения.

Опубликованные файлы версий **не изменять и не удалять**. Для обновления:

1. Добавить `data/versions/v2.json` с полным новым `saypatch-rules` каталогом.
2. Добавить `v2` в `data/manifest.json.versions`, сохранив `v1` и все старые версии;
   переключить `current` на `v2`.
3. Выполнить `npm test` и `npm run check`, собрать и выкатить новый образ обычным CI.

Все версии читаются при старте; плохой seed останавливает запуск. Поиск строится
по всем версиям, одинаковые канонические словари дедуплицируются. Runtime API
записи отсутствует; пользовательские словари расширения автоматически не публикуются.

## Локально и проверки

```sh
npm test
npm run check
npm start
# PORT=8080 BANWORDS_JWKS_URL=http://auth:8080/.well-known/jwks.json npm start
docker build -t banwords .
```

Переменные: `PORT` (8080), `BANWORDS_JWKS_URL`
(`http://auth:8080/.well-known/jwks.json`), `BANWORDS_DATA_DIR` (встроенная `data/`).
База данных сервису не нужна; данные версионируются файлами внутри образа.
Тесты работают с подменёнными JWKS/транспортами и локальным HTTP, без production,
настоящего Twitch, cookie или секретов. Проверяются seed, Unicode/UTF-16,
реальная коллизия SHA24, исторические версии, HTTP-контракт/OpenAPI, JWT,
лимиты/отказы/кеш/ротация JWKS, таймаут, конфигурация и запуск/остановка CLI.

## Деплой

По образцу `auth`: GitHub Actions → проверки → GHCR `:latest`, `:sha-*` →
SSH с отдельным forced-command CI-ключом `ci-deploy banwords`. Репозиторий
нового сервиса создаёт владелец; workflow не выполняется без commit/push.
Инфраструктура: запись сервиса в Compose без публичных `ports`,
`/api/banwords/*` через `auth_require banwords:dictionaries:read` в Caddy,
CI registry и отдельный ключ в `infra/services.yml`. Токены и секреты не
помещать в образы, seed-файлы или логи.
